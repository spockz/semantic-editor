# Advanced Go Refactoring Recipes

Read this reference only when the task calls for one of these multi-operation transformations. For operation-level boundaries and routine value extraction/inlining, use the [Go language guide](../golang.md).

## Extract state and delegate

When decomposing a large struct with grouped fields:

1. Inspect struct layout, fields, and methods with `semantic_outline`, `semantic_lookup`, and `semantic_inspect_symbol`.
2. Choose one extraction route:
   - Use `refactor_extract_type` to move a contiguous run of direct private fields, in declaration order, into a new private composed struct in the same file. Explicit owner literals may initialize selected fields as one contiguous source-order run: `cache{second: b(), first: a(), tail: c()}` becomes `cache{state: cacheState{second: b(), first: a()}, tail: c()}`. Partial initialization preserves omitted zero fields. Non-contiguous or reordered member selections, interleaved literal keys, local capture of the generated type name, implicit/aliased owner literal syntax, literal comments, source-line directives, overlapping edits, positional literals, and cross-file selected uses refuse. Candidate overlay typechecking remains mandatory.
   - Use `refactor_extract_delegate` to move one direct pointer-receiver method together with a contiguous run of private fields. The owner retains the exact method signature as a wrapper, preserving interface dispatch, method values, and method expressions. It retains its selected keyed-use refusal and also refuses receiver escape and unsupported fields, comments, generics, variadic or unnamed parameters, and named results. Nil owners pass a nil delegate so early returns preserve behavior before moved-field access.
3. Add supplemental fields with `semantic_insert_field` only when required; use `semantic_replace_construct` for inner receiver calls when needed. These operations are not a second route for fields already moved by extraction.
4. Batch compatible edits with `semantic_batch`, then verify with `semantic_verify`.

## Modernize signatures and parameter objects

When a function has too many parameters or needs a cohesive configuration value, locate typed callers with `semantic_find_references` and inspect them before editing.

- Use `refactor_introduce_parameter` to add one argument with caller updates.
- Use `refactor_introduce_parameter_object` to bundle multiple parameters into a typed struct and rewrite callers to keyed literals.
- Use `refactor_change_signature` to append one parameter with its closed argument, retain an unchanged signature, provide a complete permutation of existing parameters by `source_index`, or remove exactly one unused scalar parameter. Permutations require compiler-proven constants for all arguments at every direct call. Removal requires a compiler-proven constant only for the argument paired with the removed formal; surviving arguments keep their exact source and order, including effectful calls. Removal is limited to private nongeneric nonvariadic free functions with bodies; the removed formal must have no reads, writes, captures, or address-taking in any active variant. Tuple/ellipsis arguments, mixed additions/removals/permutations, used or nonscalar removed parameters, parameter renames, result changes, comments in rewritten regions, directives, incomplete active/test-variant caller sets, nonconstant discarded arguments, and removals that leave an unused import refuse without edits. Candidate analysis must preserve surviving argument values, effective types, and target bindings; compilation alone is insufficient.
- Use `refactor_rename` when the function or method identifier also changes.
- Verify the resulting package with `semantic_verify`.

## Extract interfaces and implement contracts

When decoupling components behind an interface, call `refactor_extract_interface` with the target file, new interface name, and selected methods. Use `refactor_implement_contract` with `panic_stub` to add missing methods to a concrete type, then replace generated placeholders with `semantic_replace_body`. Verify with `semantic_verify`.

## Evolve declarations and package structure

- Create files with `semantic_scaffold_file`; add types with `semantic_insert_type`, functions and methods with `semantic_insert_function`, top-level values with `semantic_insert_decl` or `semantic_insert_declaration`, and update package-level declarations with `semantic_replace_decl`.
- Add branches and inner control flow with `semantic_insert_case` and `semantic_insert_construct`. Append a keyed map entry or struct literal property with `kind: "element"`, `in_declaration`, an exact `discriminator`, and `source`. Struct fields use `kind: "field"` with `in_type`; positional slice/array elements remain unsupported.
- Use `refactor_move_declaration` for one supported declaration and `refactor_move_file` for a complete dependency-closed production-file declaration set within the same module. Cross-package declaration shapes and their separate proof limits are consolidated under [ADR-0090](../../../../docs/adr/0090-bounded-go-cross-package-declaration-moves.md): exported free functions; standalone exported constants with predeclared basic types and package-independent constant expressions; exported aliases whose types use only predeclared names and preserve unaliased type identity; exported variables with predeclared structural types and no initializer, or predeclared basic scalar types and constant initializers; and exported non-generic scalar or non-embedded struct types with all exported direct value and pointer methods in the selected production file. Moves target an existing production file in another package of the same main module and validate compiler-resolved references in the candidate overlay. Variable moves preserve shared storage across reads, writes, and address uses. Because interface dispatch can hide initialization dependencies, variable moves require the conservative package initialization proof across the main-module dependency closure even when imports are unchanged; dynamic package initializers, `init` functions, import cycles, destination capture, test references, and incomplete source evidence refuse. Type moves additionally prove method selections and interface relations; alias moves reject package-defined or imported type dependencies and package-sensitive private anonymous members; constant moves reject grouped or multi-value declarations, named types, `iota`, package/import dependencies, and test-file references. Cross-package moves do not guarantee external-consumer, nominal-identity, or reflection-name compatibility. File movement can include the matching test file; inspect reported dependencies and callers rather than exporting private declarations or moving unrelated files to bypass a refusal. Package `main`, `init`, linkage directives, build constraints, generated files, embeds, and relative fixture dependencies are outside the bounded file-move operation.
- Use `semantic_remove_construct` for safe collision-checked deletion, `refactor_migrate_type` for unexported fields between identical type identities, and `semantic_set_doc_comment` for declaration documentation.
- Verify after the migration. Use diagnostic reports returned by operations rather than collecting diagnostics again; unavailable or deferred diagnostic counts are not proof of a clean workspace.

## Safe deletion

Set `safe_delete: true` on `semantic_remove_construct` only when deleting an unused unexported standalone constant, eligible free function, explicitly typed package variable with no initializer, initialized basic package variable with a compiler-proven constant initializer, nongeneric defined type with empty value and pointer method sets, or an unreferenced standalone type alias. Explicitly typed zero-value variables may have any type because no initializer effects are removed. The defined-type proof applies to scalar, struct, array, slice, map, channel, pointer, function, and interface underlyings. Alias deletion does not require an empty method set because an alias does not define a distinct type; the alias itself must have no compiler-resolved references. Go checks the complete module source set, including tests and inactive build variants, then type-checks active packages and test variants. It refuses any other same-name identifier, grouped or exported declarations, generic declarations, direct or promoted methods on defined types, dynamic-import uncertainty, directives, incomplete source sets, and final normal-import uses. A batch publishes its earlier buffered segment before the disk-backed operation; it does not provide an overlay-complete safe-delete proof, and active staging refuses the operation. Ordinary removal remains structural and does not establish behavioral safety. See [ADR-0057](../../../../docs/adr/0057-exact-go-node-removal-and-safe-delete.md) for the complete boundary.

## Encapsulate a private field

For a private field whose direct reads and standalone assignments can be migrated without changing evaluation order, use `refactor_encapsulate_field` with the qualified `Type.field`, fresh private getter and setter names, and optionally an existing same-package `destination_file`. It preserves field storage and keyed initialization, rewrites typed direct reads and one-target `=` writes, and refuses unsupported uses, reflection or unsafe imports, embedded owners, and inactive build variants. Run it from the Go module root so receipts and continuations use workspace-relative paths. `auto_organize_imports` defaults to true and adds required imports for generated accessor types using compiler-resolved package identities. When false, the operation reuses a usable import or refuses before editing. In batches, required imports are included in the validated candidate; the batch-level option controls final import cleanup. Repeating a completed request refuses because the accessor names already exist; it does not act as an idempotent no-op.

## Dependencies, imports, and test assertions

Use `semantic_add_build_dependency` to add external Go modules and tidy `go.mod`/`go.sum`; use `semantic_organize_imports` to format import blocks and remove unused imports. Use `semantic_assertion_mode` to switch test assertions between fail-fast (`t.Fatal`) and continue-on-failure (`t.Error`) behavior. Verify the final package with `semantic_verify`.
