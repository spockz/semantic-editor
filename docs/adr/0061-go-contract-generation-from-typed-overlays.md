# ADR-0061: Go Contract Generation from Typed Overlays

* **Status**: Proposed
* **Date**: 2026-10-01

## Context

The Go `semantic_extract_interface` and `semantic_implement_contract` tools derive declarations from exact Go method identities and signatures. Reconstructing declarations from model-authored signature text can lose variadic markers, result names, import identity, or the distinction between pointer and value method sets. These tools also run inside buffered batches, where disk-only package analysis would ignore earlier unsaved changes and could publish outputs based on stale compiler facts.

## Decision

Implement both tools as Go-only operations over the current source buffer overlay. Use explicit recursive input and output schemas, exact `go/types` objects from the loaded package graph, and one complete candidate preflight before applying generated bytes. The extraction operation accepts a closed array of typed `{file, symbol}` method targets. Both operations require an explicit `receiver_kind` of `pointer` or `value`. Contract implementation requires explicit `body_policy: panic_stub` and emits placeholder methods that panic.

The first release writes only to an existing same-package destination file. It formats and type-checks the full candidate against the current overlay, validates the relevant read set and destination preimage, then performs one buffer apply or checked atomic publication. A no-op preserves source bytes and reports `no_op`; batch receipts describe the operation's actual working-buffer result and do not imply a whole-batch transaction.

## Invariants

* Schemas are declared, recursive, closed, and typed. Unknown keys and unsupported policy values fail before handler execution.
* Package and method identities come from the exact current overlay analysis snapshot. A selected source file digest is an opaque revision; the complete consulted-file read set is recorded separately.
* Interface extraction selects direct methods only and verifies satisfaction for the chosen receiver kind. Promoted, ambiguous, inaccessible, generic, constraint, and incomplete cases fail closed.
* Contract implementation distinguishes missing methods from incompatible or unavailable existing methods. It preserves existing method bodies and refuses a shadowed `panic` binding when generating stubs.
* Read-only analysis inputs do not gain write authority. Candidate output must parse and type-check before the one apply.
* Candidate preflight type-checks active test variants for the changed package while retaining primary compiler packages by package ID. Test variant errors refuse publication; test files inactive under current build tags fail closed when detected.
* Live receipt continuations require the final file and symbol identity plus matching revision evidence. Buffered results do not expose stale live continuations.
* Outcome states reflect actual publication or working-buffer application. Per-file publication does not imply batch-wide rollback.

## Consequences

The tools can generate signatures without model reconstruction and can participate in buffered operations that consume the same overlay. Candidate preflight checks active same-package tests so generated declarations cannot break those test variants. The explicit first-release limits exclude new-file creation, cross-package extraction destinations, generic types or methods, promoted-member extraction, constraint interfaces, inferred method bodies, and consumer rewrites. The implementation uses `go/packages` with an overlay for Go object identity and preflight; the retained MCP Go session remains responsible for the existing diagnostics, rename, and synchronization lifecycle. This decision remains proposed until implementation review and CLI/MCP evidence are accepted.
