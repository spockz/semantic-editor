# RQ-0074: Rust Refactoring Assist Contract

* **Status**: Open
* **Category**: Product & Architecture

## Question

Which Rust refactoring assists can be exposed through the shared refactoring intent vocabulary while preserving scope, evaluation order, concurrency safety, and source-buffer behavior?

## Current evidence

The Rust backend advertises lookup, rename, outline, and bounded `refactor_extract_value` (including `kind: "constant"`), `refactor_extract_callable`, `refactor_inline_value`, `refactor_inline_callable`, and `refactor_promote_local_to_const` operations. Value extraction requests the exact `refactor.extract` action with an `extract_variable:` action identity, validates its versioned single-file edit, then uses prepare-rename and rename to apply the requested local name. Callable extraction resolves rust-analyzer's lazy `extract_function:RefactorExtract:3:` action, accepts one or more contiguous direct calls to the same callee with suffixed integer literal arithmetic arguments, validates the versioned same-file edit envelope and exact helper postimage, checks a same-file implicit-unit callee and ordinary non-generic owner, and renames the inserted helper before staging. Each standalone operation attaches one authorized source buffer before its first lookup and uses that same snapshot for selection, edit validation, and publication; successful handlers flush only a buffer they own, while a batch-provided buffer remains batch-owned. It requires a conventional crate-root path in a single-source Cargo package; other Rust source files, module declarations, source-level macro or imported-name uncertainty, owner-local bindings/items/control flow, and other unproven shapes cause refusal. Requested-name collision checks use Unicode NFC. The extraction and inline-value name-expansion guard remains a conservative whole-file text check: it refuses any file containing `!`, `#`, or `include`, or containing both `use` and `*`, which can also reject comments, strings, inequality operators, attributes unrelated to name expansion, unrelated multiplication, or ordinary imports. CLI txtars cover successful value and callable extraction, including single and multiple calls, a `modify` callee, lazy action resolution, exact native edit envelopes, malformed/foreign/stale/misplaced edit refusals, unsupported selectors, ASCII and normalized Unicode name collisions, module and expansion refusals, evaluation/lifetime-order refusals, and batch overlays.

The CLI fixtures use a deterministic fake language server, including `extract_variable_rust_native_shape.txtar`, which replays the captured native edit shape through extraction, local rename, and full-file comparison. For live evidence, rust-analyzer was built from its pinned upstream source revision `2ad81e72b7e978cb800dffe1bcce5c9f98032acf` with Cargo. Version `0.0.0 (2ad81e7 2026-10-11)` returned the `extract_variable:` assist with the validated statement replacement and insertion. This proves one pinned action contract only, not compatibility across other rust-analyzer versions.

A separate live probe against the same pinned binary confirmed that `textDocument/codeAction` returns a lazy `extract_function:RefactorExtract:3:` action with kind `refactor.extract`. Resolving a direct `consume(1_i32 + 2_i32);` statement produced a version-1, same-file edit with three changes: replace the call with a generated helper call, remove the original arguments, and insert a top-level helper after its owner. A live prepare-rename/rename sequence successfully renamed both helper references. For two contiguous `consume` calls, the pinned server returned four edits: three call-site replacements (including a coalesced span reaching the owner closing brace and restoring it unchanged) and one top-level helper insertion. The backend applies these edits only when the complete candidate exactly equals the selected calls replaced by the helper invocation, all surrounding owner bytes preserved, and the validated helper inserted. The live two-call CLI operation and `cargo check --offline` succeeded. The Rust multi-call txtar replays that native envelope, checks the full result, and conditionally compiles/runs the ordered calls when `rustc` is available; a corrupt-suffix case must fail without changing source bytes. The bounded operation refuses non-conventional crate-root paths and packages with other Rust source files because a top-level helper could conflict with names visible through child-module glob imports or included source fragments. Extracting selections with live-ins/outs remains unsupported; the assist changes shape when declarations feed later statements.

The backend now exposes a narrow `refactor_inline_value` slice. It selects the binding identifier and accepts only an untyped immutable `let` initialized by one suffixed decimal integer literal, with all uses confined to simple identifier arguments on the immediately following ordinary call line. Versioned same-file `refactor.inline` edits are replayed and compared with an independently computed whole-file result; disabled or command-based actions, extra uses, and any unrelated edits are refused. `refactor_inline_value_rust.txtar` covers the CLI path and exact postimage, while unit cases cover unsafe initializer and declaration shapes. A live probe against the pinned rust-analyzer `0.0.0 (2ad81e72b7)` returned a lazy `Inline variable` action and applied its resolved edit to inline a suffixed integer used twice in the next call; rust-analyzer omitted the client-side action data from the resolve response, so validation binds the response to the original resolve request and proves the complete resulting source.

The backend now also exposes bounded `refactor_inline_callable`. A live probe against the pinned server returned a lazy `Inline`one`` action with kind `refactor.inline` and identity `inline_call:RefactorInline:0:`; resolution produced a version-1, same-file edit replacing `one()` with `7_i32` and left the callee declaration intact. The operation currently requires two same-file top-level zero-argument free functions: the callee body is one suffixed decimal integer literal with an explicit matching return type, and the caller's sole tail expression is that exact call with the same return type. The versioned edit must contain one replacement at the selected call and produce the independently derived whole-file postimage. Methods, parameters, attributes, attached documentation comments, unsuffixed or non-decimal literals, cross-file edits, stale versions, and broader inline-into-callers actions are refused. CLI txtars replay the lazy native response, check the exact output and unchanged source on corrupt/foreign/stale edits, and exercise a batch overlay after a preceding rename; Rust compilation is conditionally run when `rustc` is available.

Sol's independent reviews identified additional semantic gates for callable extraction. The backend requires the same-file callee to have an implicit unit return, which excludes an explicitly diverging `-> !` callee from this initial shape. It refuses owner-local bindings and items that could change name resolution. Cross-file glob imports remain a separate hazard, so it requires a single-source package and refuses module declarations; CLI tests assert no mutation for multi-file and module cases. Helper insertion validates the bounded same-file edit envelope and refuses non-whitespace insertion gaps that could carry attributes or documentation comments. Further work may broaden module, live-in/live-out, and helper-placement support only after new protocol and CLI evidence.

An assist inventory against the installed pinned rust-analyzer (`0.0.0 (2ad81e72b 2026-10-11)`) found additional native extraction actions. `refactor_extract_value` with `kind: "constant"` now captures the native `extract_constant` action for one direct local initializer, validates its versioned four-edit same-file transformation (typed const plus retained local alias), and renames the generated constant and alias use. The action's resolved payload omits client-side data, so resolution remains bound to the original opaque action while the complete edit is independently proven. A lexical source guard refuses possible primitive-name shadows from imports, declarations, macros, unresolved names, and generic parameters; positive decimal `+` chains are accepted only when exact integer bounds prove the fixed-width sum cannot overflow. Pointer-sized integer types and other expressions refuse. Backend and CLI txtar tests cover success, alias/import/generic refusals, overflow refusal with byte-identical source, and exact edit validation; a live CLI run against the pinned server produced the expected source. Sol 6.1 reviewed the lane and found no actionable P0-P2 findings after fixes for shadow detection, the native action envelope, and overflow.

The separate `promote_local_to_const` assist now has a distinct bounded public contract under [ADR-0095](../adr/0095-bounded-rust-promote-local-to-const.md). It accepts only an immutable fixed-width integer local initialized by a range-valid decimal literal, with exactly one use as the direct argument of the immediately following call in a simple function. It proves the uppercase generated-name absence, complete use count, native versioned same-file edit, and independently derived whole-file result. It remains separate from extract-constant. `extract_static`, `extract_module`, and observed `refactor.rewrite` assists have materially different storage, resource, or edit semantics and remain unsupported.

Sol 6.1's final review found a P2 identity-validation gap: the resolved response was decoded over the selected action, and any returned action identity or ordinal was not checked. Resolution now decodes into a fresh action, validates the required title and kind, and compares any non-null returned identity with the original lazy action identity; omitted or null data remains valid because the pinned rust-analyzer response omits it. Promotion txtars assert byte-identical standalone refusal for malformed and stale resolved edits. A buffered batch fixture stages one valid promotion, then refuses a second promotion whose resolved edit is malformed; it verifies that the failed child contributes no edit while the earlier successful child remains published, in keeping with ADR-0032's partial-success batch contract. Focused backend/operation/CLI txtar tests and the Rust-lane internal sweep pass; Sol 6.1's re-review found no actionable findings. The integrated `make check` gate follows these synchronized records.

## Investigation required

### Promote local to constant probe limits (2026-10-22)

The installed `/Users/alessandro/.cargo/bin/rust-analyzer` is pinned to upstream commit `2ad81e72b7e978cb800dffe1bcce5c9f98032acf` (2026-10-11). A live LSP probe selected the binding identifier and received a lazy “Promote local to constant” action with kind `refactor` and an action-list-dependent identity such as `promote_local_to_const:Refactor:1:`. Resolving it returned a version-1 same-file `TextDocumentEdit`: `let` became `const`, the binding became uppercase snake case, and semantic uses were renamed. The response omitted its original `data`, and no resource operations were returned. The response included an `OutsideWorkspace` entry in `changeAnnotations`, but no edit referenced that annotation. The action did not appear for the whole declaration, initializer literal, or use identifier in the plain fixture. A shorthand-field case rewrote the binding explicitly while preserving the field name. Raw protocol and semantic evidence, fixtures, and postimages are retained under `.scratch/rust-promote-local-investigation/`.

This captured response establishes only the pinned native edit shape, not safe equivalent behavior. A valid source with an inner local named like the generated constant changes into a refutable constant pattern and fails with Rust error E0005 after promotion. A valid `Drop` value compiles before and after, but its destructor moves from the local's end-of-scope position to the const item's use point, changing observed output from `after` then `drop` to `drop` then `after`. These are concrete reasons to reject blind use of the general assist. An identity fixture prints `true` both before and after, so this probe did not demonstrate an identity regression. The implemented scalar contract excludes custom and `Drop` types by requiring a proven fixed-width primitive integer, rejects generated-name occurrences and any extra source use, and independently compares the complete candidate source. Standalone/refusal and buffered-overlay txtars capture the CLI lifecycle; compiler/runtime checks establish preservation for the accepted fixture. This remains a pinned-server contract, not a cross-version compatibility guarantee.

* Investigate additional refactorings independently; do not infer support from the existence of code actions.
* The bounded native extract-constant candidate is implemented under [ADR-0092](../adr/0092-bounded-rust-extract-constant.md); future widening requires fresh action, scope, safety, and CLI evidence.
* **Complete under ADR-0095:** Sol 6.1 reviewed the implemented promote-local-to-const contract and its CLI/runtime evidence after the resolved-action identity fix. Broader scope and naming shapes remain unsupported.
* Keep the established boundary explicit: rust-analyzer actions are resolved, versioned same-file workspace edits are validated and staged, and resource operations are rejected. General multi-file/resource edit support remains unimplemented.
* Add comparable CLI coverage for supported and refused semantic shapes before advertising additional Rust assists.
* Broaden callable extraction only with fresh evidence for module namespace safety, live-in/live-out behavior, and helper-placement ownership.

## Exit criteria

Resolve this RQ only after protocol capture, lifecycle behavior, fail-closed edit validation, and comparable Rust CLI coverage are recorded for each added operation.
